== Décisions architecturales

. *Opt-in strict.* `graphify { incremental = true }` (défaut `false`). Le
   comportement actuel — scan complet, byte-identique — reste le défaut. Zéro
   risque pour les 3 consommateurs (bakery, codebase, runner).

. *Domaine `graphify.fingerprint`* (Gradle-free, objet pur) : `FileFingerprint`,
   `FileExtraction`, `SectionExtraction`, `ScanCache`, `ScanCacheStore`.
   Single source of truth de la logique d'incrémentalité.

. *Fast check `(path, size, mtime)` puis SHA-256.* Le SHA-256 n'est calculé
   *que* si le fast check échoue. Le cache d'extraction est clé par SHA-256 :
   un fichier *touché* (mtime change, contenu identique) réutilise son
   extraction sans re-parse — Loi Économie d'Encre.

. *Extracteur pur `FileExtractor` extrait de `ScanWorkspaceTask`.* Les 4
   parsers (`kotlinImports`, `adocReferences`, `tocTableReferences`,
   `agentReferences`, `sections`) deviennent une fonction pure
   `content → FileExtraction`, unit-testable, et consommée par le producteur.

. *La résolution reste hors cache.* Import → dir, refs → fichiers existants,
   dédup sections et hiérarchie `subsection` sont recalculées à chaque scan :
   elles dépendent du monde, pas du fichier. Cache = matière première, pas
   décision.

. *Le walk reste inconditionnel.* Aucune suppression d'arête cachée : le
   graphe est toujours assemblé depuis la liste de fichiers courante. Le cache
   n'accélère que la matière première.

. *Cache = un fichier JSON versionné (`version: 1`), écrit après scan.* Défaut
   `build/graphify/fingerprints.json` (gitignoré par `build/`), configurable via
   `graphify { cacheFile = ... }`. Écriture *après* succès du scan, élagué aux
   fichiers présents (empreintes mortes et extractions orphelines retirées).

. *Dégradation silencieuse.* Cache absent, illisible, corrompu ou de version
   inconnue → scan complet, jamais d'échec. Un cache est une optimisation,
   pas une dépendance.

. *Byte-identité garantie par garde.* Le functional TestKit compare le 2e run
   incrémental au 1er run octet pour octet, et vérifie que la modification d'un
   fichier est bien prise en compte (ré-analyse). Les 91 tests existants
   restent la garde de non-régression.

. *English only* — code, commentaires, Gherkin (règle transverse).

. *Méthode* : baby-step DDD/TDD/BDD strict RED → GREEN → REFACTOR, 3 niveaux
   (unit → functional → cucumber), pattern établi S-025.

== Gates et risques

* *Non-régression* : les 91 unit + 3 functional + 7 cucumber existants restent
  VERTS, sans modification de leur intention.
* *Byte-identité* : le 2e run (incrémental) doit égaler le 1er run octet pour
  octet — garde functional dédiée.
* *`mtime` non fiable* : les outils (git checkout, tar) peuvent restaurer des
  mtime. Le SHA-256 départage un contenu inchangé avec mtime neuf
  (réutilisation) ; un contenu changé avec mtime identique reste un angle mort
  standard (make/Gradle), documenté, non bloquant.
* *Cache volumineux* : ~200k empreintes = dizaines de Mo de JSON. Acceptable,
  gitignoré, hors graphe de publication.
* *Complexité* : l'EPIC touche le cœur du producteur. Découpage baby-step strict
  et opt-in par défaut neutralisent le risque.
